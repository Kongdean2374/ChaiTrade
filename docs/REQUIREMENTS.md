## 01｜產品目標與「完整」的定義

### 1.1 要做出的產品

ChaiTrade 是一套具有專業交易平台外觀與操作流程的 iOS 多市場模擬交易工具。使用者能查看行情、操作 K 線、管理自選、下單、撤單、修改委託、觀察成交、持倉及損益，並自由設定自己的虛擬本金。

操作時應有真正在使用券商或加密貨幣交易所 App 的感覺，而不是單純點選「買入」就立即增加一個數字的遊戲。

完整性包含：

- 介面、圖表、下單、撮合、帳務、風控、報表、設定、備份與建置流程彼此連動。
- 台股、美股、ETF、加密貨幣現貨、線性永續合約、外匯模擬合約、現金結算模擬期貨，以及參考指數頁面。
- 所有本機功能在 B 模式可直接運作；A 模式透過真實行情供應商執行本機模擬交易。
- 有可重複執行的測試、可追查的帳務紀錄，以及確實可產出 IPA 的雲端建置流程。

### 1.2 擬真不等於冒充

可參考專業交易軟體的資訊密度、圖表操作與委託流程，但使用自己的 ChaiTrade 品牌、版面及素材，不複製其他券商的識別或假冒正式帳戶。

App 保留低干擾但清楚的「模擬交易」標示；交易分享圖、資產報表與匯出資料同樣保留標示。不加入能偽裝真實銀行存款、真實券商對帳單或真實出金成功的功能。

### 1.3 必須坦白的技術邊界

1. **行情真實，不代表成交真實。** A 使用外部真實市場資料，但每一筆委託與成交仍由手機內的模擬引擎處理，不會進入真實交易所，也不能保證與真實排隊成交結果相同。
2. **純本機不等於全天候伺服器。** iOS 一般 App 無法依靠常駐背景程式，保證全天追價與執行委託；本案必須以明確的暫停、恢復與可驗證補算政策處理。[S03]
3. **完整 App 不等於免費取得全球全部行情。** 台股、美股、深度、逐筆與歷史資料仍受供應商權限與使用條款限制；沒有權限時顯示原因，不以合成數字假裝即時資料。[S06][S08]
4. **未簽名 IPA 不等於直接可裝機。** 雲端可產出供後續簽署的套件，正常 iPhone 的安裝與執行仍須符合程式碼簽署要求。[S04]

### 1.4 範圍邊界

本次完整交付涵蓋本文件列出的市場與功能，不把「完整」無限延伸成所有金融產品。真實入出金、真實券商下單、實際借券、實物交割、加密貨幣錢包／私鑰／鏈上轉帳、DeFi、選擇權策略、幣本位反向合約及多人共用交易所，不屬於本需求。

這些不是被延期的功能，而是與目前私人本機模擬交易定位不同的範圍。禁止為了介面看起來豐富，放入沒有可用實作的按鈕。

## 03｜A／B 雙帳戶資料模型

### 3.1 帳戶定義

| 項目 | A：線上真實行情 | B：離線模擬市場 |
| --- | --- | --- |
| 穩定識別碼 | `account-online` | `account-offline` |
| 行情來源 | 合法可使用的外部行情 API | App 內建決定性市場模擬引擎 |
| 是否需要網路 | 更新行情需要 | 不需要，且此模式禁止 App 主動連網 |
| 資金來源 | 自訂虛擬本金 | 自訂虛擬本金 |
| 委託執行 | 本機模擬撮合 | 本機模擬撮合 |
| 資料保存 | A 專屬資料庫及快取 | B 專屬資料庫及快取 |
| 時間基礎 | 市場實際時間與來源時間戳 | 獨立模擬時鐘 |
| 成交品質 | 根據真實資料能力的擬真估計 | 根據本機市場事件的模擬成交 |

### 3.2 必須獨立的資料

現金與幣別餘額、入金／減資紀錄、融資與負債、資金及持倉保留、部位、成本、所有委託與成交、手續費、稅費、資金費率、借貸利息、損益、資產曲線、績效、股務事件、自選清單、商品收藏、提醒、圖表繪圖、交易偏好、風控設定、離線市場狀態及重設紀錄，均以帳戶為範圍。

允許共用的內容僅限非財務、非情境狀態：App 語言、全域主題、字體大小、無障礙偏好、靜態圖示、開源授權及內建的唯讀規則範本。

行情 API 憑證只能由 A 的行情服務使用；B 不取得憑證、不建立 Provider，也不背景更新資料。

### 3.3 本機儲存隔離

```text
Application Support/ChaiTrade/
├── app-settings.json                 # activeMode、pendingMode、全域外觀
├── accounts/
│   ├── account-online/
│   │   ├── account.sqlite            # A 帳務與交易
│   │   ├── market-cache.sqlite       # A 有授權的行情快取
│   │   └── snapshots/                # A 本機恢復點
│   └── account-offline/
│       ├── account.sqlite            # B 帳務與交易
│       ├── market-cache.sqlite       # B 合成行情
│       ├── simulation-state.json     # 種子、時鐘、演算法版本、檢查點
│       └── snapshots/                # B 本機恢復點
└── diagnostics/                      # 去識別且不含憑證的紀錄
```

所有帳務表仍應保有 `accountID`，即使資料庫已分開，亦以雙重檢查防止錯誤匯入與服務混用。不得只靠畫面篩選同一份共用餘額，假裝兩個帳戶已隔離。

### 3.4 使用者指定案例

測試時兩個帳戶各有 TWD 100,000，價格不變、手續費與稅費為零：

- A 買入價值 TWD 10,000 的股票後：A 現金 90,000、持股市值 10,000、累計買入成交金額 10,000。
- 切換設定為 B，完整重新啟動：B 現金仍為 100,000、持股為零、累計成交金額為零。
- 切回 A 並完整重新啟動：A 的持股、委託與交易紀錄仍存在。

**成交金額、手續費、現金減少與總資產變化是不同概念。** 買入股票不等於把資產花到消失，畫面不能把「累計買入」當成「虧損」。

## 04｜模式切換與啟動生命週期

### 4.1 首次啟動

提供模式選擇、A／B 各自初始本金設定、基準幣別、漲跌配色及簡短模擬交易說明。即使先選 A，也可以事先設定 B 的起始本金；未使用的帳戶不得自動產生交易或費用。

選 B 時不要求登入、不要求 API Key，也不得等待遠端設定檔或下載圖表資源。

### 4.2 切換操作

位置：`設定 → 運作模式 → 線上真實行情／離線模擬市場`。

確認文案：

> 已設定為「離線模擬市場」。本次仍使用 A 帳戶；完整關閉並重新開啟 App 後，將載入 B 帳戶。兩個帳戶的資金、持倉與交易紀錄不會互通。

操作必須：

1. 完成當前帳務交易的原子寫入與必要檢查點。
2. 將目標寫入 `pendingMode`，不立即改變 `activeMode`。
3. 顯示目前模式與待套用模式，允許取消待套用切換。
4. 本次工作階段繼續維持原帳戶；行情、下單與頁面不可一半 A、一半 B。
5. 下次程序完整啟動時，先驗證目標資料庫、遷移與帳務，再建立目標服務。
6. 目標啟動成功後才更新 `activeMode` 並清除 `pendingMode`。

App 不使用 `exit(0)`、私有 API 或刻意崩潰實現「重啟」。返回主畫面後再切回 App，不一定代表程序已重新啟動；恢復到前景不能誤套用模式。

### 4.3 切換失敗與非作用中帳戶

若目標資料庫無法開啟或遷移失敗，保留原資料與待切換設定，提供錯誤說明及恢復方式；不得重新建立空帳戶覆蓋舊資料。

非作用中帳戶不持續運作：A 不在 B 執行期間監控行情或成交；B 不在 A 執行期間推進模擬時鐘。重新載入 A 可用新行情重估部位，但不得把未觀測期間的買賣憑空補成已成交。

### 4.4 工作階段隔離

每次啟動產生 `RuntimeEpoch`。任何網路回應、計時器、資料寫入、圖表訊息與提醒回呼，均必須綁定不可變的 `AccountContext(accountID, mode, epoch)`。

過期回呼一律丟棄。不得在回呼執行當下讀取一個可變全域 `currentAccount`，以免舊 A 回應寫進 B。

## 05｜完整商品範圍與市場商店

### 5.1 商品能力

| 類別 | 主要交易單位與功能 | 特別規則 |
| --- | --- | --- |
| 台股股票 | 股／張、整股／零股、現股買賣 | 分開交易時段、數量級距、報價盤及費率設定 |
| 台股 ETF | 股／張、現貨買賣、配息事件 | 不直接套用所有個股稅費或價格限制 |
| 美股股票／ETF | 股、允許時可碎股 | 交易所時區、日光節約時間、盤前盤後及資料範圍 |
| 加密貨幣現貨 | 幣數或報價幣金額 | 交易對、最小數量、最小名目金額、價格精度 |
| 線性永續合約 | 張／合約數、做多做空 | 槓桿、逐倉／全倉、標記價、資金費率、強制平倉 |
| 外匯模擬合約 | 基礎貨幣單位／明確定義的手數 | 匯率方向、點值、槓桿、隔夜費；不是實際銀行交割 |
| 現金結算模擬期貨 | 口／契約數 | 合約乘數、到期日、保證金、每日與最終結算 |
| 市場指數 | 行情參考，不直接買入指數本身 | 提供相關 ETF／期貨連結；合成可交易商品必須另有商品 ID |

A 中的外匯或其他自訂模擬合約，即使以真實標的行情作參考，也要標明「自訂模擬契約」，不得假稱為某券商的原生商品。

### 5.2 商品目錄／商店

「市場商店」是可瀏覽、搜尋、收藏及選擇交易標的的商品中心，不是付費解鎖商店。

必須提供市場與資產類別分類、名稱／代碼搜尋、熱門與漲跌排序、成交活躍度、商品規格頁、自選群組、最近瀏覽、停牌／下市／到期狀態，以及資料權限與可交易狀態。

A 的熱門榜、漲跌榜只能宣稱涵蓋實際收到的市場範圍；只有幾個商品時不能標成「全球排行榜」。B 的事件、排行及成交量全部標示為模擬市場資訊。

### 5.3 B 內建內容

完整交付時內建至少 120 個可交易模擬商品：30 個台股風格股票、30 個美股風格股票、20 個 ETF、20 個加密貨幣現貨、10 組外匯模擬合約、10 個線性永續／現金結算期貨商品；另有至少 5 個參考指數。

以虛構名稱與穩定的 `SIM:` 商品識別碼為預設。若使用真實公司或幣種名稱作情境參考，仍必須明示其價格為合成行情，且不得與 A 的真實商品識別碼共用。

B 支援新增自訂商品：名稱、代碼、類別、報價幣別、初始價、精度、流動性、波動率、交易時段、費率、合約乘數與是否允許做空。已有持倉時不得直接刪除商品或任意更改乘數；必須先平倉或進行可追查的規格變更事件。

採原創、深色優先的專業交易介面，同時提供淺色模式。使用一致的卡片、分隔、數字等寬字體、漲跌色、狀態徽章及小型圖表。

- 預設臺灣習慣的紅漲綠跌；可切換國際常見的綠漲紅跌。
- `A 真實行情・模擬交易` 與 `B 離線市場・模擬交易` 持續可辨識。
- 行情來源、時間與延遲狀態不可藏到深層設定。
- 金額可切換顯示／遮蔽，但不影響計算。
- 數字小數位依商品與幣別決定；不可全部強制兩位小數。
- 小螢幕、橫向圖表、較大字體、VoiceOver 及減少動態效果需可用。
- 動畫、觸覺與聲音可關閉；數值更新不能造成整頁反覆閃爍或版面跳動。

### 6.3 商品詳細頁

包含最新價、漲跌額／幅、開高低收、成交量／額、參考收盤、交易狀態、資料時間、圖表、技術指標、最新成交、買賣盤、合約資訊、自選與提醒入口，以及自己的委託和持倉摘要。

供應商未提供的資料顯示「未提供」或相應原因，不用 `0` 代替未知值，也不畫假的五檔填滿畫面。

### 6.4 下單面板

包括買入／賣出或開多／開空／平倉、委託類型、價格、數量、金額切換、數量快捷比例、有效期限、止盈止損、預估費用、可用資金、預估保證金與下單後風險。

第一次使用與高槓桿操作應有清楚說明。可開啟快速下單，但仍執行相同驗證與風控，不得繞過資金限制或資料檢查。

### 6.5 狀態完整性

每一個頁面都必須有初始、載入、無資料、無權限、無網路、資料過期、錯誤、成功與恢復狀態。失敗訊息指出原因及可行操作，例如「行情已過期，暫停新成交；恢復連線後重新報價」，不能統一寫成「未知錯誤」。

## 07｜A 模式：真實行情來源與能力管理

### 7.1 供應商實作範圍

使用統一 `MarketDataProvider` 介面，完整實作以下資料轉接器，而非只有空白 protocol 或回傳測試資料：

| 資料來源 | 本案用途 | 限制與處理 |
| --- | --- | --- |
| Coinbase Exchange 公開市場資料 | 加密貨幣現貨商品、報價、成交、委託簿與歷史資料 | 只使用行情服務；遵守條款、連線與資料能力限制。[S05][S13] |
| Fugle 股票行情 | 台股股票／ETF／指數與對應交易盤 | 使用使用者自己合法取得的行情權限；資料欄位與頻道依方案判斷。[S07] |
| Fugle 期權行情中的期貨資料 | 有授權的台灣期貨報價、成交、深度與歷史資料 | 本案只實作已定義的期貨交易模型，不因來源有選擇權就自動擴大交易範圍。[S14] |
| Alpaca Market Data | 美股／ETF 即時或延遲行情與歷史圖表 | 明示 IEX 等單一市場或綜合資料範圍，不把有限資料包裝成全市場報價。[S08] |
| Twelve Data | 外匯參考行情及可用的相關市場資料 | 實際更新頻率、幣別、可用欄位及權限依回應與方案識別；不假設一定有逐筆買賣價。[S09] |
| Binance 公開衍生品市場資料 | 已支援線性永續商品的成交、標記價格、資金費率 | 僅市場資料，不使用帳戶／委託 API；依所在地與服務可用性處理失敗。[S10] |

這是本案的整合選型，不是對服務永遠免費、無須註冊或任何地區皆可使用的保證。需要憑證的來源，支援 App 內填入與測試連線；未配置時顯示配置導引，但完整的轉接、解析、錯誤處理與測試仍須交付。

公開資料來源至少須完成一個不含私密金鑰的實際連線驗證。需帳號的來源若無測試憑證，必須標示「介面與測試完成，待使用者權限進行實際連線驗證」，不能宣稱已實測。

### 7.2 只讀網路邊界

- 所有買賣只呼叫本機 `TradingEngine`。
- 不導入可直接下單的券商／交易所交易 SDK；優先用原生網路程式讀取行情。
- 設定網路主機、路徑、方法及 WebSocket 訊息型別白名單，只允許行情、行情認證、商品規格與必要時間同步。
- 不要求銀行帳號、錢包助記詞、真實資產轉帳權限或真實下單權限。
- 若供應商憑證無法細分為純行情，優先使用專供資料或測試環境、且不涉及真實資產的憑證，並明示範圍。
- 禁止把交易結果送到外部的 paper trading 伺服器；本案即使是「模擬委託」也必須保存在手機。
- 收到不符合白名單的請求直接拒絕，並寫入去敏感化診斷紀錄。

### 7.3 資料能力分級

將資料是否即時與撮合精細程度分成兩個獨立維度。

**行情狀態：** `realtime`、`delayed`、`historical`、`stale`、`unavailable`。另外記錄來源、交易場所、涵蓋範圍、報價時間、接收時間、延遲及授權狀態。

**撮合能力：**

| 等級 | 具備資料 | 本機撮合政策 |
| --- | --- | --- |
| E1 深度型 | 有效買賣盤、數量、更新序列及必要成交資料 | 根據深度估算逐檔成交；被動排隊仍是模型，不宣稱真實順位 |
| E2 最佳報價型 | 有效買一／賣一及可用數量 | 在已知報價與數量內模擬；深度不足時不虛構真實五檔 |
| E3 參考價型 | 有效即時成交價或中間價，但缺少可成交報價 | 需明確啟用「估算撮合」，以可見的價差／滑價模型推估成交 |
| E0 不可成交 | 無資料、過期、僅歷史或不符合政策 | 可顯示圖表或保留委託，停止新成交並說明原因 |

E3 不得把估算價差當成供應商實際買賣價，成交詳情必須標記 `estimatedExecution` 與模型版本。使用者可以選擇僅允許 E1／E2。

A 預設只允許即時資料參與成交；延遲資料可看圖，不能標成「現在市場價」下單。即時與歷史資料不可混用時間軸產生套利假象。

### 7.4 資料新鮮度

分別檢查市場事件時間、來源心跳、連線狀態及接收時間。冷門商品很久沒有成交，不必然等於連線壞掉；健康心跳也不代表上一筆成交價現在可直接成交。

新鮮度門檻依市場、資料頻率與時段配置，不全市場硬套單一秒數。價差、深度、標記價與外匯估值可有各自門檻。

### 7.5 來源切換

切換來源前驗證商品、交易場所、報價幣別、交易時段與契約規格是否相同。切換後清空原來源深度、建立新快照、記錄來源事件並重新檢查未成交委託。

不得把 BTC/USD、BTC/USDT 或不同交易所報價無聲合併；不得把股價當期貨價、現貨價當永續合約標記價。

## 08｜連線、斷線與資料異常

### 8.1 連線生命週期

實作認證、訂閱、取消訂閱、心跳、逾時、限速、指數退避與隨機抖動重連。只訂閱畫面可見、自選、持倉與未結委託必要的商品，並在來源限制內調度。

HTTP 回應需區分認證錯誤、權限不足、限速、來源維護、資料格式改變及裝置離線。尊重 `Retry-After`，不要用高速重試增加封鎖風險。

### 8.2 委託簿一致性

依各供應商協定處理快照、增量與序列，不能假設所有來源共用同一套順序規則。偵測漏包、亂序或重複後，將深度標為不可撮合，重新取得快照並依協定套回增量。Coinbase 官方亦說明序列缺口與亂序處理的重要性。[S13]

有效深度必須符合價格排序、數量非負及來源快照的一致性；不明確的交叉盤須依市場狀態暫停或等待重建，不直接當作可無限套利。

### 8.3 A 斷線政策

- 帳務、歷史與既有持倉仍可查看。
- 未成交單保留，不自動改成 B 的合成行情。
- 未知期間不產生新的成交、價格觸發或估計強平紀錄。
- 撤單可以在本機完成；恢復後不得讓已撤單再次成交。
- 重連後顯示「監控曾中斷」及時間範圍，再依有效新行情恢復。
- 持倉估值保留最後可用價格與其時間，不能顯示成即時。

恢復服務時，先處理可由明確時間與已知規則確定的 DAY／GTD 到期，以及有可靠資料支持的交割、利息或費用事件，再允許新成交。資料不足的費用標示待核對，不能默認為零或猜測補扣。這是當下執行的帳務恢復，不是宣稱 App 在背景持續運作，而且只能影響對應帳戶。

### 8.4 不回填虛構成交

預設不根據離開期間某根 K 線的最高、最低價，補做已成交交易。OHLC 無法單獨證明事件順序、可成交深度或排隊順位。

完整歷史成交資料可用於研究型回放，但若啟用，必須另列為明確的「回放估算」事件，不能假稱實際監控期間成交。正式 A 帳務預設不啟用這種回補；歷史圖表補齊與委託補成交是兩件不同的事。

## 09｜圖表、指標與技術分析

### 9.1 圖表選型

採 `WKWebView + 本機打包的 Lightweight Charts` 作為主交易圖表，SwiftUI 作為頁面與下單介面；簡單資產曲線可採原生 Charts。

Lightweight Charts 是圖表工具，不是完整 TradingView 交易終端。資料、指標計算、繪圖工具、委託線與互動需由本案實作；保留所需的 LICENSE、NOTICE 與產品出處標示。[S11]

JS、CSS、字體及圖示必須隨 App 封裝，不依賴 CDN 或遠端網頁。B 在首次安裝後無網路仍應正常顯示圖表。

### 9.2 必備功能

K 線、折線、成交量、1 分／5 分／15 分／30 分／1 小時／4 小時／日／週／月週期、縮放、拖曳、十字游標、最新價格、OHLC 顯示、橫向全螢幕、重置視角、歷史分頁與即時最後一根更新。

不支援的來源週期可由可靠的較細資料向上聚合，但不得用一根日 K「拆出」假分鐘 K。空白時段、非交易日及尚未完成的 K 線要有一致政策。

### 9.3 技術指標

必須實作 MA、EMA、MACD、RSI、KD、布林通道、VWAP、ATR 與成交量。參數可調、可儲存、可重設，並可管理主圖與副圖。

每個指標都有明確公式、暖機資料需求、缺值處理、測試向量與數值容許誤差。VWAP 的交易時段與重置基準需依市場設定，不把跨日資料無限累加。

### 9.4 繪圖與交易覆疊

提供水平線、趨勢線、垂直時間標記、矩形區域及 Fibonacci 回撤。繪圖依帳戶與商品保存，可選取、修改及刪除。

顯示成本線、委託價格、停損停利線及買賣成交標記。拖曳委託線會開啟改單確認，不得直接繞過數量、保留資金及價格精度驗證。

### 9.5 圖表資料正確性

原始價格、成交與帳務使用精確十進位；轉為繪圖用浮點數只發生於呈現邊界，不回流成財務計算輸入。

區分原始價格與還原價格。還原價可供分析，但不能直接作為當時實際成交或結算價格。重複、亂序、跨時區與夏令時間的資料必須經標準化後再進圖表。

## 10｜委託種類與狀態機

### 10.1 必須完整實作的委託

| 類型 | 行為 |
| --- | --- |
| 市價單 | 依當前有效流動性與價格保護成交，不保證全部瞬間成交 |
| 限價單 | 買入不高於限價、賣出不低於限價，未符合時保留 |
| 停損市價 | 觸發後產生具價格保護的市價委託 |
| 停損限價 | 觸發後產生限價委託，可能觸發但未成交 |
| 停利條件單 | 以明定觸發價與方向形成對應退出委託 |
| 移動停損 | 按絕對價差或百分比追蹤有利方向極值 |
| OCO | 兩單共組，一單首次成交後原子取消另一單；餘量及保護狀態清楚呈現 |
| 括號委託 | 主單成交後，按實際成交部位建立／調整停利與停損保護 |

有效期限涵蓋 DAY、GTC、GTD、IOC、FOK。Post-only、Reduce-only 及平倉數量限制，依商品模型提供。不是每個市場都原生支援所有委託；App 提供的本機條件單必須明示其為 App 條件控制。

### 10.2 核心狀態

```text
Draft → Validating → Rejected
                 └→ Accepted → Working → PartiallyFilled → Filled
                                      ├→ Cancelled
                                      └→ Expired
```

條件觸發狀態、暫停原因與生命週期分開保存，例如 `triggerState=armed`、`suspensionReason=staleQuote`，避免暫停後遺失「已部分成交」資訊。

每次狀態轉換保存時間、原因、操作來源、原始委託 ID、事件序號及規則版本。狀態不可倒退；已完成委託不得重新進入可成交狀態。

### 10.3 資金與部位保留

委託成立時保留最大合理資金、費用與所需持倉。保留只是限制可用額，不是實際支出。

買單須同時計入費用與保護價格；賣單不能把同一批股票重複保留給兩張互不相依的委託。OCO／括號單共用退出數量保留，避免兩張保護單把持倉凍結兩次。

### 10.4 改單、撤單與重複操作

改價、改量視為可追查的修訂，依市場規則處理時間優先順位。額外資金不足時維持原單，不先撤掉原單再悄悄失敗。

雙擊下單、回呼重送、重啟恢復及網路重連都透過穩定 `clientRequestID` 與冪等檢查避免重複成交。取消與成交同時發生時，以交易引擎的事件順序決定結果，並在同一資料庫交易內落地。

### 10.5 保護單細節

OCO 與括號單不能混為同一語意。一般 OCO 首次成交後取消另一單；若只平掉部分部位，清楚顯示剩餘部位是否仍受保護。括號單的保護組則跟隨主單已成交量及剩餘部位更新，不能超額反向開倉。

Stop 的觸發參考可為成交價、標記價或買賣報價，依商品提供並固定存入委託。委託已成立後，不因全域設定變更而悄悄換觸發依據。

## 11｜本機撮合引擎

### 11.1 基本原則

所有成交都由單一序列化寫入者處理。同一個事件處理中完成驗證、流動性消耗、委託更新、部位更新、帳本分錄與統計事件；任何一步失敗則整體回滾。

不得在 View 中直接扣錢或加持股，不得由多個頁面各自建立一套交易邏輯。

### 11.2 成交模型

- 市價買單依賣盤，市價賣單依買盤，不一律使用畫面上的最後成交價。
- E1 可依深度逐檔計算成交均價；E2 依有效最佳報價與保守數量處理；E3 使用明示的估算模型。
- 限價成交必須遵守價格限制；僅「碰到價格」不代表能無限量成交。
- A 被動排隊以保守估計模型處理，保存模型版本、參考成交量及估計品質。
- B 由本機委託簿、模擬市場參與者與事件產生流動性，不能為使用者憑空提供無限對手盤。
- 同一份可用深度不得在同一事件中被多張單重複使用；A 模擬消耗不會改變真實市場，需以一致的本機影子流動性管理方式處理。
- 滑價、價差、部分成交、延遲與拒單都有明確參數與可追查原因。

### 11.3 價格保護與成交失敗

市價單設定最大可接受偏離或資金上限，超過時停止剩餘成交並回報未成交量。不能為了保證「購買成功」讓現金無限制變負。

FOK 須先對整筆可成交量作原子預檢，不能先成交一半才發現不足；IOC 可立即成交一部分並取消餘量。Post-only 若會立即吃單，按所選規則拒絕而非偷偷當市價單。

### 11.4 成交事件必備資訊

`fillID`、`orderID`、`accountID`、商品、方向、數量、價格、費用、稅費、報價來源、報價時間、處理時間、撮合能力等級、模型版本、估算標記、流動性事件 ID、規則版本及關聯帳本分錄。

### 11.5 費率計算

支援 maker／taker、固定費、比例費、最低費用及商品稅費設定。最低手續費依設定以委託或適用結算單位計算，不能把每次部分成交都重收一次最低費用。

實際市場費率與稅率以有來源、有生效日期的規則包管理；內建的娛樂用自訂費率明示為模擬設定，不宣稱為所有券商的現行規定。

<a id="section-12"></a>

## 12｜財務帳本、成本與資產計算

### 12.1 數值安全

金額、數量、價格、匯率、費率與損益使用可檢查溢位的十進位運算。不得以 `Float`／`Double` 作為財務真實值，也不得以 SQLite REAL 保存帳務金額。

採 `Decimal` 封裝的 Money／Price／Quantity 型別與標準化十進位字串儲存；需要固定尺度整數的地方，必須有明確尺度、範圍及溢位檢查。除法、乘法及捨入必須處理錯誤，不得將 NaN、Infinity 或精度遺失寫入帳本。

輸入上限依引擎可安全表示的範圍設定；可提供很大本金，但不是宣稱無限精度。所有捨入方向由商品及費用規則決定，保留原始計算與結算值以供核對。

### 12.2 會計來源

使用不可直接覆寫的帳本分錄與交易事件作為財務來源，餘額、持倉及績效可由這些資料重建。修正錯誤採沖銷／調整事件，不修改舊成交價掩蓋問題。

每一幣別的雙邊分錄必須平衡，涉及不同幣別的換匯透過各幣別清算分錄處理，不能直接把 TWD 與 USD 相加宣稱帳平。商品數量另有部位子帳，與成本帳相互核對。

### 12.3 餘額分類

```text
已結算現金 = 可用現金 + 委託保留 + 保證金鎖定 + 其他受限現金
```

未結算應收、應付、借款、借券負債、費用與累積利息另外記錄。買進可用額可以依規則包含某些應收，但不能因此把應收同時計入兩次現金。

### 12.4 淨值估值

```text
帳戶淨值
= 現金
+ 現貨多頭市值
- 現貨空頭的市值負債
+ 衍生品未實現損益
+ 應收
- 應付
- 現金借款
```

各項先按自身幣別計算，再以有來源、有時間的匯率轉換為基準幣別。保證金屬於受限資產，不能被當成費用扣除後又再次加回。衍生品名目本金不直接加進帳戶總資產。

缺少有效匯率或價格時標示「估值不完整／使用最後已知價格」，不能用零代替未知資產。USDT、USDC 與 USD 是不同資產，不能默認永久 1:1。

### 12.5 成本與損益

預設採加權平均成本作為 App 的模擬績效口徑，保留每筆交易明細與成本批次。部分賣出、完全平倉與反手開倉必須分別處理已實現與新部位成本。

顯示毛損益、費用、稅費、資金費率、利息及淨損益；同時區分交易損益與匯率換算損益。不得把人工增加本金或匯入資產列為投資獲利。

### 12.6 自訂本金與資金操作

A／B 分別提供建立帳戶時的起始本金、自訂多幣別餘額、虛擬入金、虛擬減資與完整重設。

使用者輸入「我想把總資產設為某金額」時，先顯示目前淨值及所需資金調整，確認後以入金／減資分錄處理，不直接修改持股市價或刪除虧損。存在凍結資金與持倉時，不允許任意減到破壞資金限制。

設定中的本金操作不使用「真實銀行轉帳成功」等用語。

## 13｜放空、保證金、槓桿與強制平倉

### 13.1 產品區分

現貨帳戶預設不允許負持倉；做空必須切到允許借券或合約的商品規則。融資股票、外匯模擬合約、永續與到期期貨不能只靠同一個「槓桿倍數」欄位實現。

### 13.2 必備功能

做多／做空、單向持倉與雙向持倉模式、逐倉／全倉、調整槓桿、追加／移除保證金、初始與維持保證金、風險比率、預估強平價、Reduce-only、部分減倉及強制平倉紀錄。

全倉只共用同一 A 或同一 B 帳戶內、同一明確風險群組允許的抵押資產，絕對不能跨 A／B。不同結算幣別未設定抵押折扣與轉換規則時，不自動共用資金。

### 13.3 風控依據

永續優先使用對應商品的標記價格與明確的維持保證金級距。若來源無標記價，不可直接宣稱最後成交價就是交易所標記價；自訂模型須標示，且由使用者明確選擇。

風險評估須包含未實現損益、費用、資金費率、利息、保留委託與減倉成本。強平不能簡化為「價格跌了 1／槓桿倍數就一定爆倉」。

### 13.4 資金費率、利息與到期

依商品資料或明示模擬規則處理資金費率與下次結算時間，不把所有合約硬寫成固定每八小時。資金費事件使用唯一 ID，重啟或重連不得重複扣款。[S10]

期貨每日結算與最後結算需處理現金變動及成本基準重設，避免已結算損益又留在未實現損益中重複計入。近月與次月是不同商品；連續期貨圖表不可當作可直接交割的實際合約。

### 13.5 暫停與跳空

A 在未監控期間不能保證及時強平。恢復後按第一個有效風險價格重新評估，必要時執行「恢復後風險處理」，保留中斷與跳空結果，不捏造中途成交時間。

若虛擬帳戶出現穿倉，記錄負債與限制新開倉，不能把餘額無聲歸零。可以由使用者明確選擇重設帳戶，但不得自動掩蓋紀錄。

## 14｜市場規則、交割與股務事件

### 14.1 規則包

每個市場／商品的 `RulePack` 包含：時區、交易日曆、開收盤與集合競價狀態、最小跳動、數量級距、最低名目金額、價格限制、委託能力、費率、交割日計算、借券／保證金規則、合約乘數及生效期間。

規則包附 `source`、`effectiveFrom`、`verifiedAt` 與 `ruleVersion`。使用者自訂值要有「自訂模擬」標記，不能悄悄蓋掉已標為交易所規則的內容。

已成立委託與成交保存當時規則版本；變更費率或商品規格不回頭重寫歷史。

### 14.2 市場時鐘

使用交易所 IANA 時區及日曆，內部時間戳採 UTC。美股日光節約時間、跨午夜的交易時段、假日、臨時休市及不同盤別要分開處理。

台股整股與零股不得共用不相符的成交盤；盤前盤後不可自動套用正常時段市價單政策。不得將全市場寫成「平日某個固定本地時間」。

### 14.3 交割模型

提供擬真交割與簡化即時交割兩種帳戶設定，預設採有明確規則包的擬真交割。簡化模式必須清楚標記，其改變的是本機資金可用與結算流程，不代表真實交易市場的制度。

交割日透過交易日曆計算，不能用固定小時數代替營業日；日曆未驗證時標示估算，相關規則不得宣稱完全符合現行制度。

### 14.4 股務事件

支援配息／股息、分割、反向分割、商品代碼變更、停止交易、下市及現金清算事件。

分割後數量、每單位成本、未完成委託、條件價與圖表都需依政策調整，總成本不能無故改變。股息區分除息、應收與入帳；不要同時把價格調整與股息重複算成損益。

A 只使用可信來源事件或使用者明確輸入的人工事件；缺少來源時顯示未同步。B 可以產生模擬事件，但明示是模擬，不冒充真實公司公告。

## 15｜B 模式：完整離線市場引擎

### 15.1 完全離線的定義

B 的商品、行情、深度、圖表、新聞事件、成交、指標、帳務、說明與介面資源都在裝置內。第一次開啟、不曾使用 A、沒有 API Key、飛航模式下，也必須可完整操作。

B 不執行遠端設定、連線檢查、字體下載、圖表 CDN、分析追蹤或更新檢查。要開啟外部授權頁等外連操作時，必須由使用者明確發起並提示將離開離線操作環境。

### 15.2 市場生成模型

不能只讓每個商品在固定區間獨立亂跳。模型至少包含：

- 市場狀態：多頭、空頭、盤整、恐慌與復甦。
- 市場共同因子、產業／資產類別因子與個別商品波動。
- 波動率群聚、跳空、趨勢延續、均值回歸及流動性改變。
- 價格、成交量、價差、深度及短期市場衝擊之間的關聯。
- 台股、美股、加密貨幣與外匯各自的市場時鐘與波動特性。
- 高流動性與低流動性商品的不同滑價、深度與成交機率。

可採分段市場狀態＋對數報酬模型作為起點，但須經固定種子測試與情境檢查。隨機模型用浮點計算的結果，必須量化為合法價格跳動後，才可進入交易引擎；價格不可變成負數或超出數值安全範圍。

### 15.3 可重播的隨機性

儲存 `simulationSeed`、演算法版本、模擬時間、各因子狀態、商品狀態、事件序號、已排定事件及檢查點。使用固定規格的偽隨機演算法，不使用不穩定的系統雜湊作為種子映射。

同樣的種子、演算法版本與使用者事件序列，應產生相同的價格、成交與帳務結果。切換頁面、多看一張圖或產生縮圖，不得消耗核心隨機序列而改變未來市場。

行情生成、模擬對手盤與使用者交易的隨機來源分流；資料匯出及 UI 動畫不影響市場。更改演算法版本時記錄變更點，不重新生成已成交期間的行情。

### 15.4 價格、K 線與成交資料的一致性

定義單一權威事件序列及固定時間粒度，再向上聚合 K 線。不同圖表週期不能各自抽一組亂數。

歷史資料採按需生成與分段快取：內建商品提供至少一年日 K 的可生成能力，並提供近期 30 個交易日的一分鐘歷史；不要求首次啟動就把所有商品全部展開到記憶體。

若採階層式時間生成，細粒度路徑必須與已確立的粗粒度 OHLCV 相容。當前尚未結束的 K 線只能反映已經走到的事件，不能提前露出預先生成的最高價、最低價或收盤價。

增加歷史範圍、縮放、換週期或重啟後，已觀測價格不能變動。成交量、委託簿、最後成交與 OHLCV 要能對得起來。

### 15.5 模擬對手盤

建立具有不同價差、補單頻率、成交方向與流動性限制的模擬市場參與者。使用者市價單消耗可用深度；大單產生滑價或依模型形成後續短期衝擊。

無委託、無持倉的商品可按較低成本生成摘要；涉及觸發、成交及強平的區段，必須採可保持結果一致的細粒度事件處理。不得只因某張畫面未開啟，就讓該商品的停損失效。

### 15.6 市場事件與新聞

內建財報超預期／不如預期、股息、分割、產業利多、政策衝擊、交易中斷、流動性枯竭、加密市場急漲急跌等事件。

新聞卡片與市場事件共用同一事件 ID；影響何時開始、持續多久、影響哪些因子都可追查。事件不保證單向價格反應，也不保證使用者能靠固定新聞模式獲利。

B 新聞全部顯示「模擬事件」，不得使用不實的真實公司重大消息混充現實新聞。

### 15.7 模擬時鐘與控制

提供 1×、2×、5×、10×、60×、100×、暫停／繼續、跳至下一交易時段及指定情境。速度改變的是市場時間，不是直接乘上損益或重複觸發費用。

加速時減少 UI 更新次數，但不丟掉交易事件。跳轉時間需先按順序處理委託、股務、費用與到期事件，不能只改畫面日期。

### 15.8 離開 App 後的 B 行為

提供兩種明確設定：

| 設定 | 行為 |
| --- | --- |
| 離開時暫停 | 回到前景從原模擬時間繼續 |
| 離開時持續時間，重開補算 | 依保存的時鐘與事件序列補算；預設離開期間以 1× 推進，前景加速倍率不自動延伸到數日背景 |

預設採第二種，首次使用即說明「關閉時不在背景執行，重新開啟才補算」。補算要有進度、分批檢查點、取消／暫停及崩潰後恢復能力。

當切到 A 後，B 的模擬時鐘暫停。B 再次被選為作用中帳戶時重設牆上時鐘錨點，不把整段使用 A 的時間算進 B。

長時間離開不得直接跳過持倉風險區間或把缺口全部歸零；需要大量補算時顯示實際進度，先完成影響帳務的事件，再開放交易。可以讓使用者明確放棄該段推進並從檢查點繼續，但不能無提示改寫歷史。

### 15.9 沙盒控制

僅 B 提供市場波動、事件密度、流動性、情境預設及自訂商品等控制。變更保存時間與內容，預設只影響未來事件。

重新抽市場種子涉及重建世界，必須要求備份與確認；存在持倉／未結委託時不得悄悄替換歷史。A 不提供手改真實行情價格的功能。

## 16｜前景、背景、通知與時間完整性

### 16.1 明確的執行保證

A 只有在程式取得執行時間、行情有效且引擎運作時，才能偵測並處理新的條件。一般背景排程不能提供固定頻率或全天候保證，因此不以背景計時器、持續 WebSocket 或本機通知假裝伺服器。[S03]

退到背景時原子保存帳務與必要狀態、停止不必要訂閱及圖表更新。短暫背景執行時間只用於完成必要保存，不濫用音訊、定位或其他背景能力維持交易。

### 16.2 通知範圍

提供價格到達、漲跌幅、委託成交／拒絕、保證金風險、離線補算完成及資料中斷提醒。

- A 的價格提醒由實際正在運作的引擎偵測，沒有伺服器時不承諾鎖屏後仍即時通知。
- B 補算才發現的事件顯示「補算發現」與模擬發生時間，不假裝在當時推播。
- 通知與 App 內通知中心共用事件 ID，避免重啟後重複發送。
- 通知依帳戶隔離，非作用中帳戶不繼續生成新事件。
- 使用者拒絕通知權限時，交易與帳務功能仍正常，事件留在 App 內。

### 16.3 裝置時間變動

使用單調時鐘處理工作階段內經過時間，UTC 時間戳記錄可讀事件；跨啟動時檢查時鐘倒退、異常大跳及時區變更。

A 依來源時間與可信時間資訊判斷新鮮度；B 不能因調整手機時間而重複領取股息、重複觸發資金費或跳回已成交之前。異常時停止自動補算並要求明確選擇處理方式。

## 17｜持倉、績效、交易日誌與報表

### 17.1 資產頁

提供總淨值、可用資金、受限資金、未結算應收應付、借款、各幣別餘額、部位清單、成本、現價、未實現損益、已實現損益、倉位比例、保證金與風險狀態。

持倉可依資產類別、商品、幣別與損益排序，點入後能看到加減倉歷史、費用、持有期間、保護委託及直接平倉操作。

### 17.2 績效統計

包括日／週／月損益、淨值曲線、已實現與未實現拆分、勝率、平均盈虧、盈虧比、最大回撤、交易次數、成交金額、費用占比、平均持有時間及依市場／商品的績效分布。

勝率以明確定義的已結束交易週期計算，不把每次部分成交都當成一筆獨立勝利。樣本不足時顯示不足，不用除以零或產生誤導性百分比。

### 17.3 資金流與績效分離

至少提供：

1. 實際淨值曲線：呈現本金調整對資產的影響。
2. 扣除外部資金流影響的績效曲線：使用已定義並測試的時間加權或單位淨值方法。
3. 累計入金、減資與交易淨損益的對帳摘要。

最大回撤的基準與是否扣除資金流要標示清楚。匯率缺值、監控中斷或資料不完整區段不得用平滑曲線掩蓋。

### 17.4 交易日誌

每筆委託／交易可加入備註、策略標籤、情緒／原因標記及交易前後檢討。這些屬於使用者本機資料，不傳到外部服務，不在公開儲存庫中附帶範例真實內容。

可儲存本機產生的交易圖表截圖；匯出時保留模擬交易與帳戶模式標示。

### 17.5 匯出內容

提供 CSV 交易／委託／資金帳本、JSON 結構化資料、持倉與績效摘要，以及可還原的專用備份格式。所有匯出包含模式、帳戶 ID、資料截止時間、估值完整性與資料版本，不包含 API 金鑰。

CSV 對可能被試算表當作公式執行的備註或商品名稱做安全處理；金額與日期格式應有可機器解析的欄位，不能只輸出帶千分位與幣別符號的顯示字串。

## 18｜備份、還原、重設與資料遷移

### 18.1 備份方式

提供單獨備份 A、單獨備份 B、完整備份兩個帳戶，以及建立重設前恢復點。透過 iOS 檔案選擇器儲存，使用者可自行選擇本機或自己管理的檔案位置；App 不自動上傳到自有雲端。

備份包含 `manifest.json`、資料版本、帳戶模式、建立時間、檔案清單、校驗值、帳本、必要規則快照、繪圖／提醒、B 的種子與模擬狀態。行情快取預設不輸出；確有需求時仍須符合來源允許的保存與使用範圍。

### 18.2 一致性與憑證

使用 SQLite 一致性備份或經驗證的快照流程，不只複製主資料庫檔而忽略 WAL 中未合併資料。交易資料、投影及事件序號必須落在同一個一致時間點。

API 金鑰與裝置生物辨識資料不進備份。換裝置或更換簽署 Team／Bundle ID 可能影響資料容器與 Keychain 存取；安裝說明必須提醒先備份，不能保證任意重簽都保留所有資料。

### 18.3 還原流程

先解包到暫存區、驗證檔案安全與校驗值、檢查帳戶類型與資料版本、執行遷移、核對帳務，最後才原子取代目標帳戶。

A 備份不得直接當 B 匯入，反之亦然。提供明確的「取代此帳戶」確認，不預設合併交易紀錄，也不把歷史 ID 重新編號造成重複事件。

任何驗證失敗，原帳戶必須完全不變。解包需防止路徑穿越、過大檔案、壓縮炸彈、重複路徑及不合法資料結構。

### 18.4 加密與重設

備份提供密碼加密選項，使用成熟的認證加密與經審查的密碼衍生方式，保存演算法及參數版本；不自行發明加密方法，不把 CryptoKit 的對稱金鑰直接當作人類密碼使用。

帳戶重設要二次確認並明示影響範圍，可選擇先備份。只重設 A 不得刪除 B；清除行情快取不得刪除交易；刪除 API Key 不得重設本金。

### 18.5 資料遷移

所有 schema 變更都附可重複測試的遷移。更新失敗時保留原始資料及恢復點，不允許以「資料格式更新」為理由直接清空帳戶。高版本備份不能被低版本靜默截斷讀取。

## 21｜效能、耗電與穩定性目標

以下為待實機量測的驗收目標，不能未測試就標記通過。

| 情境 | 目標／量測方式 |

測試報告列出裝置、OS、工具鏈、資料量、場景、p50／p95 與實際量測方式。模擬器結果不能冒稱 iPhone 實機結果。

### 21.1 快取政策

已成交帳本與交易歷史不可自動清理。可重建的圖表快取、來源快照與診斷資料可依容量限制清理，但帳戶設定、B 的權威事件與恢復檢查點必須保留足夠資料，確保結果不變。

資料量過大時先通知並提供匯出／封存，不默默刪除最舊交易。

### 21.2 並行安全

UI 更新在主執行緒；行情解碼、指標計算、離線市場與報表在適當隔離服務執行。Actor 或等效序列化機制必須配合資料庫交易，不能把 `actor` 當成跨資料庫原子性的替代品。

停止或切換服務時清理 Task、訂閱、觀察者與 WebView 訊息處理器，防止重複監聽、記憶體洩漏與舊事件污染。

## 22｜安全、隱私與公開專案要求

### 22.1 不得進入公開儲存庫的資料

Apple ID 登入資訊、App Store Connect 私鑰、`.p12`、`.mobileprovision`、個人 API Key／Secret、真實銀行或交易帳戶資料、個人資料庫、Keychain 匯出、私人交易備份、真實使用者截圖及包含敏感資訊的診斷紀錄。

`.gitignore` 與 CI 機密掃描須同時涵蓋原始碼、設定、測試資料與建置產物；不能只把金鑰藏在 Swift 常數、Base64 或公開 GitHub Actions 變數中。

### 22.2 金鑰與本機保護

API Key 由使用者在 App 內輸入，保存於 Keychain，預設只在裝置解鎖時供 A 的資料來源讀取，不同步到其他裝置。金鑰欄位遮蔽顯示，可刪除、替換及測試。

帳務資料採 iOS 檔案保護。可提供 Face ID／裝置密碼 App 鎖定，但須區分「介面鎖定」與「備份加密」，不能宣稱前者自動保護所有已匯出的檔案。

### 22.3 網頁圖表安全

圖表只載入隨 App 打包的本機資源，限制導覽與外部請求。Swift／JavaScript 橋接訊息有 schema、長度限制、商品及帳戶驗證；不將供應商字串直接插入可執行 JavaScript。

圖表端不能直接寫入資料庫或呼叫遠端委託端點。買賣互動只產生經主 App 驗證的意圖事件。

### 22.4 日誌與診斷

預設不接第三方分析、廣告與遠端崩潰上報。診斷封包由使用者主動匯出，先遮蔽金鑰、認證標頭、含金鑰的 URL、帳戶識別與備註內容。

記錄的重點為事件類型、錯誤分類、序號、版本、效能與資料品質，不保存完整憑證或無限制的原始網路封包。

### 22.5 授權與行情使用

自有程式碼預設規劃採 MIT 授權；第三方函式庫、圖表、字體與素材各自保留原授權。實際建立儲存庫時須確保所選授權與所有依賴相容。

公開程式碼不代表可以公開重新散布付費行情。測試 fixture 使用自行生成、符合官方 schema 的資料，或明確允許使用的範例；不得把個人取得的授權行情資料庫直接一起推上 GitHub。[S06][S14]

## 24｜GitHub Actions 與未簽名 IPA

### 24.1 公開建置原則

使用公開 GitHub 儲存庫與標準 GitHub-hosted macOS runner。GitHub 官方目前將公開儲存庫的標準託管 runner 使用列為免費，但這不代表所有較大型 runner、儲存或其他服務均無限制免費；實際政策以官方文件為準。[S01][S02]

本案不需要自建 Mac、不需要在 CI 放 Apple 登入，也不需要為了編譯提供市場資料金鑰。

### 24.2 工具鏈與可重現性

在 `.ci/toolchain.json` 記錄 runner 類型、Xcode、Swift、iOS SDK、模擬器 runtime、依賴與前端資源版本。開始實作時依官方 runner 映像清單選用可用且合適的工具鏈，完成驗證後鎖定，不憑記憶硬寫已淘汰的 macOS 標籤。[S02][S15]

每次建置保存 commit SHA、工具鏈、依賴鎖定摘要及建置編號。版本升級需透過明確依賴更新，不自動跟隨第三方最新 main。

### 24.3 觸發與權限

- `workflow_dispatch`：供使用者從 GitHub 網頁手動建置。
- 主要分支程式碼變更：執行核心測試、UI 冒煙及 device build；純文件變更可跳過重型建置。
- Pull request：執行不需要 Secrets 的驗證；不使用帶敏感權限的 `pull_request_target` 執行不可信程式碼。
- 預設 `permissions: contents: read`；只有明確需要的個別工作取得更高權限。
- 設定相同分支的 concurrency，取消被後續提交取代的非必要建置。
- Actions 與第三方下載固定至經核對的版本／commit；下載工具需驗證來源與完整性。

### 24.4 必要工作流程

1. Checkout 程式碼並確認依賴鎖定檔。
2. 檢查工具鏈、必要 SDK、可用模擬器及專案 Scheme。
3. 檢查授權檔、圖表資源、內建商品目錄與規則包。
4. 執行核心單元、資料庫遷移與固定種子整合測試。
5. 執行模擬器 UI 冒煙與 A／B 隔離測試。
6. 使用 iPhoneOS SDK 建置 Release `.app`，關閉開發者憑證簽署。
7. 驗證 `.app` 的平台、架構、Info.plist、資源與嵌入元件。
8. 封裝成 `Payload/ChaiTrade.app` 結構的 IPA。
9. 掃描產物是否誤含憑證、描述檔、金鑰或使用者資料。
10. 產出 SHA-256、建置資訊、測試摘要及未簽名 IPA。
11. 上傳有限保留期的 Actions artifact，預設保留 7 天，避免無限制累積。

### 24.5 建置命令基準

以下是實作腳本的命令形狀，供開發者依已建立的專案驗證；不是宣稱本文件已執行此建置：

```bash
#!/usr/bin/env bash
set -euo pipefail

ROOT="$(pwd)"
APP_NAME="ChaiTrade"
DERIVED_DATA="$ROOT/build/DerivedData"
PACKAGE_DIR="$ROOT/build/UnsignedPackage"
OUTPUT_DIR="$ROOT/dist"

xcodebuild \
  -project "$ROOT/ChaiTrade.xcodeproj" \
  -scheme "$APP_NAME" \
  -configuration Release \
  -sdk iphoneos \
  -destination 'generic/platform=iOS' \
  -derivedDataPath "$DERIVED_DATA" \
  CODE_SIGNING_ALLOWED=NO \
  CODE_SIGNING_REQUIRED=NO \
  CODE_SIGN_IDENTITY="" \
  DEVELOPMENT_TEAM="" \
  clean build

APP_PATH="$DERIVED_DATA/Build/Products/Release-iphoneos/$APP_NAME.app"
test -d "$APP_PATH"

mkdir -p "$PACKAGE_DIR/Payload" "$OUTPUT_DIR"
if [[ -e "$PACKAGE_DIR/Payload/$APP_NAME.app" ]]; then
  echo 'Package destination already exists; use a clean build directory.' >&2
  exit 1
fi

/usr/bin/ditto "$APP_PATH" "$PACKAGE_DIR/Payload/$APP_NAME.app"

# 專案必須實作此驗證器；驗證失敗不可繼續發佈產物。
"$ROOT/scripts/verify_artifact.sh" "$PACKAGE_DIR/Payload/$APP_NAME.app"

IPA_PATH="$OUTPUT_DIR/$APP_NAME-unsigned.ipa"
if [[ -e "$IPA_PATH" ]]; then
  echo 'IPA output already exists; use a clean output directory.' >&2
  exit 1
fi

(cd "$PACKAGE_DIR" && /usr/bin/zip -qry "$IPA_PATH" Payload)
/usr/bin/shasum -a 256 "$IPA_PATH" > "$IPA_PATH.sha256"
```

正式腳本應自行從 repo 根目錄定位、支援乾淨輸出、保留錯誤日誌並處理執行環境。不得為了產出未簽名檔案而強行走需要正式簽署的 App Store export 流程。

### 24.6 產物檢查

- 必須是 iPhoneOS device 產物，不是把 iPhone Simulator `.app` 壓成 IPA。
- 檢查 Mach-O 平台與架構、最低系統版本、Bundle ID、執行檔與資源完整性。
- 不包含私人 Team、簽署憑證、`embedded.mobileprovision` 或個人 Keychain。
- 檢查主程式及嵌入元件的簽署狀態；工具鏈若產生不具裝機授權的 ad-hoc 標記，須與 Apple 裝機簽署清楚區分，不假稱可以直接安裝。
- 圖表 JS／CSS、商品目錄、在地化、圖示與第三方授權必須存在。
- IPA 完整解壓驗證、checksum 與建置資訊必須一致。

### 24.7 使用者安裝界線

交付未簽名 IPA 後，由使用者使用自己的有效簽署方式處理。文件說明所需裝置／描述檔條件及重簽前備份，不提供或索取他人的憑證，不保證任何一種第三方簽署工具永遠有效。[S04]

## 25｜測試策略與逐項驗收

### 25.1 測試層級

**單元測試：** 數值、捨入、指標、費率、委託驗證、成交、成本、保證金、強平、交割、時區及事件冪等。

**性質／不變量測試：** 以多組固定種子與隨機委託序列檢查帳本平衡、成交量限制、資金保留、OCO 不超賣、重播一致、A／B 不污染，以及任意失敗點恢復後仍一致。

**整合測試：** 來源解析、斷線／重連、快照與增量、資料庫交易、背景恢復、備份／還原、schema 遷移及公開建置。

**UI 與實機測試：** 主要流程、各種空狀態、縮放與下單、鍵盤、橫向、無障礙、飛航模式、性能與重新啟動。

### 25.3 精確帳務測試向量

以下均為合成數據，不代表任何實際市場：

**向量 A：無費用現貨。** 本金 100,000，以 100 買入 100 股後現金 90,000、成本 10,000；以 110 全部賣出後，假設即時交割，現金 101,000、已實現損益 1,000、持倉與保留皆為零。

**向量 B：費用。** 同上，買賣各收 10，稅費為零；最終現金 100,980、毛價差 1,000、總費用 20、淨損益 980。成本口徑需與報表一致，不能再扣第二次費用。

**向量 C：加錢不算賺錢。** 無持倉帳戶本金 100,000，人工增加 50,000 後淨值 150,000，交易損益仍為零，資金流調整後報酬率為零。

**向量 D：分割。** 持有 100 股、總成本 10,000，執行 1 股拆為 2 股後為 200 股、每股成本 50、總成本仍為 10,000；價格與委託按指定政策調整，不平白產生獲利。

### 25.4 測試報告規則

每一項狀態只能填寫 `通過`、`失敗`、`未執行` 或 `外部條件阻擋`，並附 commit、測試方法與證據位置。不得把未執行改寫成通過，也不得將供應商憑證缺少寫成「功能不需要做」。

核心財務、帳戶隔離、備份與無真實交易邊界有任何失敗，皆不可宣稱達成完整驗收。實機尚未測試時只能寫「CI／模擬器驗證完成，待實機驗證」。

## 30｜主要風險與處理決策

| 風險 | 本案處理 |
| --- | --- |
| 希望像真實券商，但完全無後端 | 明定本機執行邊界，A 停止無資料成交，B 採可重播補算 |
| 免費行情不足以覆蓋所有市場 | 多 Provider、能力分級、使用者自帶合法權限，拒絕偽造即時資料 |
| 雙模式資料污染 | 雙資料庫、不可變 AccountContext、epoch、獨立快取及隔離測試 |
| UI 看似完整但交易邏輯缺漏 | 以帳務不變量、端到端流程與需求對應測試驗收 |
| 浮點誤差與重複事件 | 精確數值、受控捨入、原子交易、唯一鍵與冪等 |
| B 加速或長時間補算不一致 | 固定時間語意、權威事件、版本化種子、檢查點及重播測試 |
| 帳戶重設／更新造成資料遺失 | 一致性備份、原子還原、遷移測試與失敗不覆寫 |
| 公開原始碼洩漏機密 | 不放機密、Keychain、掃描、合成 fixture 與產物驗證 |
| 圖表或工具鏈版本變更 | 鎖定依賴、保留授權、CI 前置檢查及升級測試 |
| 模擬報表被誤認為真實資產 | App、截圖分享與匯出持續保留模擬標示 |
